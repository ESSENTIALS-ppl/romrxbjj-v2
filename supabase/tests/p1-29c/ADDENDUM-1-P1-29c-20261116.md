## Why this addendum

Grant (9:01 PM ET) asked for a read-check of the 26 edge functions the earlier athletes-column check did not cover (14 of 40 already covered), before P1-29c is applied. 29c drops `coaches_select_athletes` and recreates six dependent policies (`coaches_select_assessments`, `coaches_insert_assessments`, `drill_sessions_coach`, `game_plans_coach`, `completions_coach_read` on `protocol_completions`, `ps_coach` on `protocol_sessions`) TO authenticated through `coach_linked_athlete_ids()`.

The receipt's section 1 ("Column usage proof") cited `get_edge_function` sources for **five** functions, with file sha256 in `logs/deployed-source-sha256.txt`. Those five hashes still match live tonight. The receipt does not name a list of 14 edge functions. To avoid skipping a function that was not actually in that cited five, this addendum read-checks **all 35** not cited there (and reconfirms the five). If the intended "14 covered" was a broader informal set, nothing in the other 26 was skipped.

Tables in scope: `athletes`, `assessments`, `drill_sessions`, `game_plans`, `protocol_completions`, `protocol_sessions`. Question: does any function read them with a **user JWT** client (anon key + the caller's `Authorization` header), especially as a coach, so that 29c would change or break behaviour? Service-role clients bypass RLS and are unaffected.

## Verdict

**No deployed edge function will break or change behaviour when 29c is applied.**

The only user-JWT reader of any of the six dependent tables is `export-my-data` v4 (ezbr `45dd9300`). It does not read `athletes`. It reads the caller's **own** rows of `assessments`, `protocol_sessions`, `protocol_completions`, `game_plans` and `drill_sessions` (explicit `eq(owner, uid)`), not as a coach. 29c's coach policies do not change that.

No function uses a user-JWT client to read these tables as a coach. Coach screens still go through service-role functions (`get-coach-roster`, `coach-actions`, `ai-chat`), which bypass RLS.

## Method

- `list_edge_functions` returned 40 ACTIVE functions (9:03 PM ET). Versions below are those live numbers. The receipt labelled the same objects one version lower (`get-coach-roster` v21 vs live v22, etc.) with the **same** `ezbr_sha256`; the cited file sha256 values still match, so the sources have not changed.
- Every function was fetched with `get_edge_function` and matched to the live `version` + `ezbr_sha256`.
- "User JWT" means `createClient(url, ANON_KEY, { global: { headers: { Authorization: <caller> } } })` (or equivalent) used for a table read. A user-JWT client used only for `auth.getUser()`, with table access on a separate service-role client, is service-role only.
- Retired functions that return 410 and have no database client are "no access".

## export-my-data v4 (the only user-JWT hit)

- Live: v4, ezbr `45dd9300cc48c01ae31d9e76685fbff27de8b96125e57312d97efe08d38030f7`, `verify_jwt` true.
- Source sha256 tonight: `d2d4cc2dde9a95c40a3f282838ebcfb26e5ae630ba5985bb44a04f57ed80ce45` index.ts, `0f665af7f27e512e313ac6113b4bbe74c4ba4f1e4c099d22381d0650db2facd5` handler.ts.
- Client: caller's JWT only. index.ts:8-10: "The caller's own JWT: RLS applies. No service-role key is read by this function." `userClient` is `createClient(url, ANON_KEY, { global: { headers: { Authorization: authHeader } } })`.
- handler.ts SPECS (lines 75-88) include, among other owner-scoped tables: `assessments` (owner `user_id`), `protocol_sessions`, `protocol_completions`, `game_plans`, `drill_sessions`. **`athletes` is not in SPECS.**
- Every page is `db.from(table).select(cols)` with an explicit `.eq(s.owner, uid)` (handler.ts:173-174, :192-193). The file comment (handler.ts:4-5) states this filter is required because `game_plans` also has a public-select policy.
- Coach-authored rows about the athlete are excluded on purpose (handler.ts:20).
- After 29c, a linked coach's JWT could in principle see linked-athlete rows through the six recreated coach policies (same as today through `coaches_select_athletes` and the current dependents). The explicit `eq(owner, uid)` still keeps the export to the caller's own rows. No behaviour change, and no break.
