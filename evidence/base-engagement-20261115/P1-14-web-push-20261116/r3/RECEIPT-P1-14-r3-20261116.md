## 2. 404/410 cleanup (Grant call 2)

On a 404 or 410 from the push service, for that user only:

- If the candidate has a `push_subscriptions` row id, delete that row (`id` + `user_id`).
- Null `notification_preferences.push_subscription` only when the stored endpoint matches, including after a table-row clear, so `listDue` cannot resurrect the same dead endpoint via the jsonb fallback.
- Release the `push_sends` claim (`user_id` + `dedupe_key`) so the 404/410 is **not** counted as the day's send. A second live device for the same user can still claim and send in the same run. `cleared` increments; `sent` and `failed` do not.
- Non-gone failures still increment `failed`, keep the claim, and do not clear.

Dry-run: the response includes `would_clear` (always 0, because dry-run does not call `send` and cannot observe a 404/410) and `cleared: 0`. `clearDead` and `releaseClaim` are not called. No write. Tests stub fetch to throw and assert zero fetches, zero clears, zero claims.

## 4. Side finding: save-push-subscription silent reassign — REAL, fixed in r3

See `r3/SIDE-FINDING-save-push-subscription-20261116.md`.

Live `index.ts:17` updates `push_subscriptions` by endpoint only and writes `user_id` to the caller (no `.eq("user_id", …)`). `handler.ts:8` documents "Re-points an existing device row to this user"; `handler.ts:41` calls that touch. Because `endpoint` is UNIQUE, this silently moves the row from one user to another.

r3 fix: `touch` matches only the caller's rows and does not write `user_id`. A cross-user endpoint is deleted from the previous owner and inserted as a fresh row for the caller (new id). If the caller is already at the 10-device cap, return 409 and leave the other row. The live jsonb write (`notification_preferences.push_subscription`) is kept. hello@ support clause stays dropped.
